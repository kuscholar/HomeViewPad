# Architecture and privacy

SwiftUI application, iPadOS 17+, no packages, no app-owned server. The checked-in Xcode project contains app, XCTest unit tests, and XCUITest UI tests. Its generator uses only Python's standard library.

- `Dashboard.swift`: responsive presentation, sheet navigation, foreground state, display preferences, and adaptive widget board. Native controls provide keyboard/VoiceOver semantics. Scrolling and flexible card grids handle changing size classes. Text uses semantic styles except the intentionally scalable hero clock. Active states include text, not color alone. There is no essential animation or continuously running presence camera. Foreground standby keeps the dashboard rendered beneath a transparent touch-to-wake surface and pauses slideshows and weather requests.
- `HomeModel.swift`: main-actor HomeStore with separate deterministic demo fixtures and a lazily created real HMHomeManager. HomeKit delegates hop to the main actor. A generation token ignores completions from abandoned connections. Existing homes and services are discovered; all supported readable characteristics become typed tiles, including secondary characteristics on a service: power, temperature, humidity, brightness, target temperature and fan speed. Numeric writes require the device's minimum, maximum and step, writable permission, reachability and a valid current value. Temperature, humidity and target-temperature tiles belong exclusively to the climate hero; target temperatures appear first. Its arrows validate device-advertised steps and bounds and use the same write/read-back path. Demo target changes only update deterministic in-memory fixtures. Writes are not optimistically successful. Per-characteristic in-flight controls block repeats until write and read-back complete. Event notifications clear earlier read failures. Scenes ask for confirmation and block concurrent execution. Empty, restricted, unresolved, and unreachable homes have distinct states and retry actions.
- `AccessoryAdjustmentView.swift`: explicit numeric adjustment and Apply action; unavailable values disable writes.
- `PhotoLibraryStore.swift`: opt-in PhotoKit albums and single-image PhotosPicker import, generation-guarded image requests and a bounded 2048-pixel decoded image. Full access permits album enumeration; limited access displays only authorized images. A change observer refetches after edits/deletions, and foreground transitions recheck authorization. The photo panel never writes to the Photos library.
- `WidgetCarousel.swift`: reusable square slot with directional vertical transitions, bounded position dots visible during a vertical drag and for one second after switching and named accessibility actions.
- `OverviewBoard.swift`: opaque black two-by-two square composition with date, numbered clock, shared PhotoKit album and weather. Launches as the first page. Demo uses a fixed weather fixture; live mode observes WeatherStore.
- `WeatherStore.swift`: native Apple WeatherKit client and Apple city geocoding, city and units persistence, in-memory weather, 15-minute foreground refresh, cancellation/generation guards and explicit offline/stale states.
- `WeatherLocation.swift`: lazily creates CLLocationManager only outside demo, requests When In Use permission and a city-scale one-shot fix, reverse-geocodes through Apple, and falls back to Philadelphia on denial/failure. No background location mode.
- `PhotoWall.swift`: full-screen album composition, large digital clock and shared image crossfades. A `PhotoFrame` identity changes only when decoding completes.
- `Services.swift`: EventKit read-only providers, AVPlayer and AirPlay bridge, and a camera session with a 20-second connection timeout and explicit teardown. Camera presentation uses `HMCameraView`; no stream is saved. Lifecycle transitions pause audio and stop camera streaming.

## Data lifecycle

HomeKit owns the home database and permissions. HomeViewPad does not export its home model. Home selection is available in Settings; its stable identifier is remembered. The first available home is used when the saved home no longer exists. Connection mode, display-awake preference and personal-display preference are in app-scoped UserDefaults, declared in the privacy manifest. No accounts, tracking SDKs, telemetry endpoints, analytics or external credentials exist. The optional live weather feature uses Apple WeatherKit and Core Location geocoding.

A single imported photo is downsampled and stored as `Documents/ambient-photo.jpg` in the app sandbox. Remove it in Settings or uninstall the app. This file may be included in the device's ordinary backup; HomeViewPad has no sync service. The single-photo picker only gives the chosen image. Album mode instead stores the selected collection identifier and rotation preference in app-scoped UserDefaults, fetches only visible image assets, and does not create a local album copy. A missing/restricted selected album is never silently replaced by All Photos. Image requests are cancelled on source changes and inactivity; stale completions cannot restore removed photos. iCloud images may download through PhotoKit when displayed. The app never changes or deletes library assets. Removing displayed photos clears its selection and imported copy. Only the visible Home screen, Overview board, or Photos wall advances the 30-second slideshow; other pages, sheets and background activity pause it.

Calendar and reminder data is loaded only after system consent and the shared-screen opt-in; read-only results remain in memory. Disabling personal display or leaving the foreground clears them. A generation token prevents an earlier refresh from restoring cleared results. A foreground privacy cover helps obscure content during inactivity; physical observation of an unlocked shared screen remains possible. Any system permission can be revoked in iPad Settings.

Audio uses a security-scoped URL only for the current selected file; selecting another file releases the old scope. No permanent bookmarks or credentials are created. AirPlay selection is entirely system-mediated. The app has no background audio mode.

## Maintainability boundaries

No SwiftUI view issues accessory writes directly. HomeStore provides a small command surface. Demo fixtures never instantiate HMHomeManager. Hardware-specific errors are displayed instead of replaced with sample values. Simulator tests validate app flows and fixture state, not HomeKit hardware correctness. Scene effects, remote reachability, signing entitlement and camera/AirPlay compatibility require the separate hardware checklist.

The current first version does not implement thermostat mode/lock/blind editors, automation creation, multiple concurrent camera streams, notifications, or household identity. Add these as isolated adapters with real-device tests, rather than broadening demo-only claims.


## Immersive navigation revision

`DashboardPage` defines Overview, Home, Clock, Photos and Settings; Overview is the initial page. The immersive board fills `min(width,height) - 16` points and uses an explicit square frame for every slot, including the clock. The application requests hidden status bar and persistent system overlays using public SwiftUI APIs; the system can still reveal its own chrome. A tap recognizer on the uncovered wallpaper toggles navigation without intercepting widget buttons. Navigation overlays the bottom in portrait and the right side in landscape without resizing the board. The full-screen photo wall also accepts a background tap. Music remains a navigation shortcut. Overview has four fixed widgets (no widget carousel); it fills the entire viewport background with black and preserves square cells in both orientations. Its album opens the existing photo chooser. The clock draws white ticks, numerals and hands with a yellow seconds hand, without material or borders.

`DashboardSwipe` rejects short and ambiguous diagonal drags. The root handles horizontal directions only; each widget handles vertical directions only. Independent slot offsets select disjoint content groups: climate; clock/calendar; photos/camera; scenes; other devices; lights. Empty groups show category-specific placeholders; they never borrow another stack’s items. Changing a widget never issues a hardware command. Offsets are session state and survive page changes; home/room changes reset them to avoid carrying another home's selections across contexts. Existing scenes still require confirmation in their current presentation context.

The large-text layout retains square widgets in a single scrolling column. Vertical drags scroll this accessibility layout; named Next widget / Previous widget actions provide switching without competing with scrolling. Every slot also exposes Show navigation, and the page exposes next/previous page accessibility actions. The demo disclosure is integrated into the first widget. The Home wallpaper contains no personal data. The separate Photos page intentionally displays the chosen photo library content across the screen.

## Transition and photo loading lifecycle

Page transitions slide horizontally; widget transitions slide vertically, following the gesture direction. Navigation appears from the bottom or right according to orientation. Reduce Motion substitutes short fades. Each widget displays a maximum of five position dots; the active indicator and accessibility value identify its selection even in large homes.

The photo loader keeps the current authorized image while requesting the next one. It publishes the new frame, position and asset ID together only after a successful decode. The Home photo widget, Overview album widget and wall crossfade between frame identities. Permission loss, a missing selected album, removal or replacement cancels requests and clears the frame immediately; clearing does not animate a revoked image out slowly. The wall clock uses real time in live mode and the fixed fixture date in labeled demo mode.

## Weather and location

Live mode defaults to Philadelphia. With When In Use permission, Core Location requests approximately three-kilometer accuracy and Apple reverse geocoding supplies a city label. The coordinate sent to Apple Weather is rounded to two decimal places (about one kilometer). The location manager is lazy and never starts in demo. Background transitions stop location work; weather task work is cancelled when its visible task ends. Automatic location is rechecked at most every 15 minutes while weather is visible. Manually selecting a city disables automatic following until Use current location is selected again. Location denial/failure falls back to Philadelphia.

City searches use CLGeocoder and coordinates are rounded to two decimal places. Coordinate-based search-result IDs replace the old GeoNames IDs; previously saved manual cities remain compatible. Native WeatherService requests current conditions and daily forecasts, preserving Apple's localized condition and SF Symbol (including day/night variants). Temperatures normalize to Celsius before local display-unit conversion. Attribution is fetched through WeatherService and cached in memory with the reading. Both the tile and panel display the Apple Weather mark and a legal-source link; no real reading is published unless attribution is available. No REST key, third-party endpoint or app-owned weather backend is required. The app entitlement and project generator both enable WeatherKit, but the publishing team must also enable the App ID's WeatherKit capability/service and regenerate provisioning. Paid membership includes a shared monthly quota, not unlimited per-user requests; see [Apple WeatherKit](https://developer.apple.com/weatherkit/).

Unsigned simulator UI tests accept either real WeatherKit data with attribution or an explicit unavailable state, and do not certify live authorization. A separate Debug-only `--uitesting --weather-preview` fixture checks attribution layout with a visible TEST WEATHER label; it never substitutes for live-service failure, does not request location, and cannot be enabled in Release. Demo continues to use its original fixed weather with a DEMO label and makes no weather requests.

Weather readings and automatically detected coordinates remain in memory. Manual city selection, follow-location preference and units use UserDefaults. The provider may log requested coordinates/searches; the privacy manifest declares unlinked coarse location and search history for app functionality. No GPS point is sent to HomeKit or to an app-owned server. API errors retain a previous reading with an offline label; readings older than an hour are marked outdated. Failures retry after two minutes, successful refreshes after fifteen. A city/mode change clears old readings and invalidates in-flight callbacks. Demo never requests weather or location and does not substitute fixture readings for live failures.

## Foreground standby and wake

`StandbyStore.swift` owns an opt-in, default-off state machine: awake → dimmed/listening → optional bounded TrueDepth check → awake or listening. It preserves the user's brightness and restores it on touch, confirmed detection, disabling the feature, or leaving the active scene. The idle timer is disabled only while the app is active and either Keep screen awake or Standby is enabled. Settings, open panels, confirmations/errors and app audio playback suspend standby. It never locks or unlocks iPad, grants authentication, or brings an inactive app to the foreground.

`StandbySensors.swift` uses AVAudioEngine while dimmed, reducing temporary input buffers to RMS sound levels without retaining audio. Twelve initial buffers estimate the noise floor. Standard sensitivity uses max(-55 dBFS, floor + 8 dB), with Low (-40, +17) and High (-65, +6) options. Two consecutive buffers above the threshold or one buffer at least 8 dB above it trigger a wake or check; quiet input rearms the gate. This admits shorter and quieter events that the previous fixed -38 dBFS/two-buffer rule rejected. These are initial tuning values, not measured accuracy or range guarantees. Sound mode uses no camera and is the default for users without an explicitly saved wake mode. Explicitly saved TrueDepth selections are preserved. A retained in-memory detection result distinguishes sound wake, face-confirmed wake, and no-face/timeout outcomes. Optional input/threshold levels can be displayed for sensitivity checks; no raw audio is retained. Sound + TrueDepth stops the microphone, opens only the built-in front TrueDepth camera, and pairs Vision face rectangles with synchronized depth. Two matching frames with median central-face depth in 0.2–2.0 m qualify. Both outputs must support the same rotation; unsupported capture fails closed. The store requests teardown after three seconds including startup; the capture queue also ends after 2.5 seconds of running. A blocked system startup/stop can delay physical teardown and must be measured on hardware. Failed checks have a 15-second start-to-start cooldown. Quiet arrivals may be missed; sounds from TV, pets or other sources can trigger checks. Darkness and pose can prevent the RGB-based face detector from succeeding even when depth exists.

Enabling the feature or changing its wake mode in settings requests the required microphone/camera consent. Missing permissions or unsupported selected hardware block dimming and display an actionable status. A microphone startup error, interruption, or no audio buffers within four seconds restores brightness and blocks further dimming until the user retries in settings or toggles the feature. No regular-camera fallback, continuous camera session, background mode, wake-word recognition, identity matching, files, or network transmission is added. iPadOS privacy indicators remain visible. Audio interruption or a route/reset event stops sensing and restores brightness; retry requires user action in settings. Original audio-session category/mode/options are restored on stop. Real AirPlay and other-app audio coexistence require device validation.

Wake, mode changes and inactivity invalidate generation tokens so delayed callbacks cannot restart sensing or restore an old state. Demo uses explicit labeled simulated sound/face controls and never requests permissions or starts microphone/camera capture. Preferences use app-scoped UserDefaults; audio, image, face and depth buffers are transient on-device processing, not collected data. No new collected-data entries or background entitlements are added to the privacy manifest.

See Apple's [capture rotation documentation](https://developer.apple.com/documentation/avfoundation/avcaptureconnection/videorotationangle) for matching video/depth buffer orientation. Simulator tests cover state, cancellation and presentation; they do not establish physical sensor timing, presence accuracy, power savings or App Store review acceptance.
